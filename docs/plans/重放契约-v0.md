# 重放契约 v0

生成时间：2026-04-21。
适用范围：EvalShield v1。

## 目的

这份文档定义 EvalShield v1 中“replay”到底是什么意思。

replay 的存在，是为了加强 run trust 评估。
replay 不是为了保证普遍意义上的完全确定性。

## 核心原则

v1 保证 **structural replay**。
v1 可以选择性尝试 **behavioral replay**。

如果不把这两者明确区分开，replay mismatch 很快会变成高噪声、低解释力指标。

## Replay 模式

### Structural replay

Structural replay 验证：

- 相同 canonical input bundle
- 相同 task metadata references
- 相同 diff / repo-context references
- 相同 prompt references
- 相同环境指纹类别
- 相同 trace topology 预期
- 相同 evidence path 可解析性

Structural replay 问的问题是：

- 我们能否重建这次 run 的结构与证据链？

### Behavioral replay

Behavioral replay 尝试验证：

- findings 是否相近
- verdict 是否相近
- review-output behavior 是否相近

Behavioral replay 问的问题是：

- 重新运行后，行为是否仍然具有实质相似性？

Behavioral replay 在 v1 中是 best-effort。

## v1 承诺

v1 必须支持：

- structural replay
- explicit replay status
- recorded run 与 replay run 的 divergence summary

v1 不承诺：

- 字节级完全一致的 output replay
- 普遍性的 semantic equivalence judgment
- 跨 provider drift 的稳定行为

## Replay 必须 pin 或引用的输入

Replay 必须 pin 或引用：

- `source_run_id`
- canonical bundle digest
- benchmark name + version
- adapter name + version
- model identifier
- prompt refs 或 prompt digest
- diff digest
- repo context refs
- environment fingerprint
- 如存在则 pin tool trace refs
- replay mode

如果这些信息缺失，replay 应该被标记为 unavailable 或 failed，不能靠猜。

## Replay Status

允许的状态值：

- `completed`
- `unavailable`
- `failed`

### 语义

- `completed`：replay 已执行，并产生了 comparison 结果
- `unavailable`：因缺少前提条件，根本无法尝试 replay
- `failed`：replay 已开始，但执行未成功完成

replay status 必须始终显式。

## Divergence 语义

### Structural divergence 示例

- input digest 不一致
- 缺失 required prompt refs
- environment fingerprint 不匹配
- evidence pointers 无法再解析
- trace topology 出现实质变化

### Behavioral divergence 示例

- verdict 发生变化
- primary reason codes 出现实质变化
- findings 集合出现实质变化
- review output 的结构变化影响 trust interpretation

## 什么不算 replay mismatch

以下情况在 v1 中不应自动算 replay mismatch：

- review text 的无害措辞变化
- 不影响 verdict 的次序微调
- 不影响 trust 的正常模型非确定性

## Replay 与 Verdict 的关系

### 规则

Replay 是 trust policy 的输入，不是独立真相源。

### 示例

- replay unavailable + 其他都干净 -> `suspect`
- structural mismatch，且 evidence path 断裂明显 -> `suspect` 或 `invalid`，取决于 verdict policy
- 单纯 behavioral drift，但没有 structural issue -> 通常是 `suspect`，不是自动 `invalid`

## ReplayBundle 最低内容

```text
ReplayBundle
- source_run_id
- source_run_digest
- replay_mode
- replay_status
- replay_inputs_ref
- replay_environment_fingerprint
- replay_trace_ref
- replay_output_ref
- divergence_summary
```

## Failure Handling

Replay 相关失败必须显式表示：

- 缺少 replay 前提 -> `unavailable`
- replay 执行崩溃 -> `failed`
- environment mismatch -> `unavailable` 或 `failed`，取决于发现时机

Replay failure 绝不能被静默转换成 trusted outcome。

## v1 工程规则

Replay 的实现顺序必须是：

1. structural replay contract
2. replay bundle writing
3. divergence summary
4. optional behavioral replay experiments

禁止一开始就从 behavioral replay 起步。

## 明确不做

- 跨所有 provider 的完全 deterministic sandbox replay
- 针对 review outputs 的 semantic-equivalence engine
- browser/computer-use benchmark replay

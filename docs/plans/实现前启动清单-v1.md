# EvalShield 实现前启动清单 v1

生成时间：2026-04-22。
适用范围：EvalShield v1。
定位：这是**实现前最后一道门**。

它不重写设计。
它把“现在可以开始实现什么、按什么顺序、先验证什么”压成可执行清单。

## 0. 启动前总规则

开始实现前，先默认下面三条：

- 不修改项目边界
- 不新增第二 benchmark family
- 不在实现里偷偷补平台能力

如果某个实现动作需要改：

- 宪法
- 契约
- verdict 规则
- replay 边界

先停。先改设计文档。再继续实现。

## 2. 当前允许实现的范围

### 允许

- contracts
- contract validation
- exemplar ingest
- normalization
- detector interfaces
- reason-code registry
- first-pass detector scaffolding

### 不允许

- dashboard
- hosted API/service
- browser benchmark support
- policy/approval features
- plugin system
- generic benchmark orchestration
- second benchmark family

## 3. 第一波实现目标

第一波目标不是“EvalShield 跑起来”。
第一波目标是：

> 把 canonical contracts + exemplar ingest + loud failure path 做成最小可信闭环。

做到下面 4 条就算第一波通过：

1. canonical contracts 可被实例化和校验
2. exemplar fixture 可被 ingest
3. malformed input 会 loud fail
4. 实现没有违反已冻结设计边界

## 4. 第一波实现顺序

顺序固定：

1. contracts
2. validation tests
3. exemplar ingest
4. normalization
5. detector interface

先不要做：

- trust engine 细节
- replay engine 细节
- casebook pipeline 细节

原因：这些都依赖前面稳定。

## 5. 第一波建议任务

### Task A1

目标：

- 建立 `RunArtifact`、`DetectorFinding`、`TrustVerdict`、`EvidenceRef`、`ReplayBundle`、`CaseRecord`

验证：

- contract validation tests 通过

### Task A2

目标：

- 把 digest/version/pointer/reason-code 相关规则写进实现校验层

验证：

- 非法字段、非法 pointer、缺失版本字段会 fail loud

### Task B1

目标：

- 支持 `pr_review_generic_v0` exemplar ingest

验证：

- exemplar fixture -> canonical bundle 成功

### Task B2

目标：

- malformed exemplar 输入报 contract error，不静默吞掉

验证：

- 错误路径测试通过

### Task C1

目标：

- 写 detector protocol/interface，不写复杂 detector 逻辑

验证：

- detector 只能吃 canonical `RunArtifact`

## 6. 开工前必须先回答的 5 个问题

每次开始一个实现任务前，先问：

1. 我现在改的是不是 `run trust`，不是别的问题？
2. 我是不是还在服务 PR review benchmark？
3. 这块是不是已有权威文档？
4. 我这次是在实现设计，还是偷偷改设计？
5. 这个动作会不会把项目拉向平台化？

如果第 4 题答案不是“实现设计”，先停。

## 7. 第一批测试清单

第一批必须先有：

- contract validation tests
- digest/version field tests
- evidence pointer parsing tests
- exemplar normalization tests

第一批先不要写：

- full replay semantic tests
- full detector golden tests
- end-to-end CLI happy path tests

## 8. 命名纪律

实现阶段必须遵守：

- `casebook` 是逻辑层名
- `cases/` 是磁盘真相目录
- 不再发明：
  - `casebook_store`
  - `corpus_store`
  - `incident_archive`

如果实现里出现这些词，说明开始漂移。

## 9. 变更纪律

出现以下情况，必须先停下来改文档：

- 想增加新 contract 字段
- 想增加新 reason code
- 想让 replay 承诺从 structural 扩到 behavioral
- 想支持第二 benchmark family
- 想把 CLI 变成更完整产品表面

顺序必须是：

1. 改对应 spec
2. 改 implementation plan
3. 再开始实现

## 10. 启动完成定义

只有满足这 4 条，才能宣布“实现阶段正式开始”：

1. 必读文档已读完
2. 第一波实现范围已确认
3. 第一波测试目标已确认
4. 第一波任务顺序已确认

## 一句话总结

现在可以开始实现。
但只能开始 **contracts + exemplar ingest + loud failure path** 这条最小闭环。

# EvalShield 决策台账 v1

作用：记录已经锁死、后续默认不再重复讨论的关键决策。

## D1. 项目一句话定义

`EvalShield` 是面向 PR-review benchmark runs 的 benchmark trust layer。

## D2. v1 主战场

v1 只做 PR review benchmark，不做第二 benchmark family。

## D3. 输入策略

v1 输入顺序固定：先 artifact ingest，后 live hooks。

## D4. 接口形态

v1 只提供 CLI 和 Python library。

## D5. 核心问题

项目要回答的是“这次 run 是否可信”，不是“agent 整体能力有多强”。

## D6. 三条主判定轴

v1 只围绕：
- leakage
- exploit
- replay mismatch

## D7. 最小不可再删能力集

v1 只保留：
- run capture
- detectors
- trust engine
- replay + evidence pack

## D8. 生态形态

EvalShield 生态是：core repo + casebook / corpus，不先做插件系统。

## D9. Canonical truth source

外部 benchmark 输出不是事实真相源。事实真相源是 EvalShield canonical bundle。

## D10. Replay 边界

v1 只承诺 structural replay；behavioral replay 只允许作为实验性能力存在。

## D11. Case 原子单位

casebook 原子单位是：一次 suspect / invalid run + evidence + interpretation。

## D12. 第一 exemplar

v1 第一套 exemplar fixture 固定为 `fixtures/pr_review_generic_v0/`。

## D13. 文档权威顺序

```text
项目宪法
  > 主文档
  > 契约与规范
  > 实施计划 / 启动清单
  > 决策台账 / 术语表
  > 导览文档 / README
```

## D14. v1 / v1.1 永久非目标

以下内容在 v1 / v1.1 都不做：
- 在线服务 / hosted service
- dashboard / web UI
- 通用 benchmark 平台
- 通用 agent security / policy / approval
- browser/computer-use 扩展

## D15. 当前阶段纪律

当前仍处于设计阶段。
在这些内容稳定前，不进入大规模实现。

## D16. README 与导航文档不是权威规则源

以下文档只负责导览与摘要：
- `README.md`
- `docs/plans/文档导航.md`

## D17. `casebook` 是逻辑层名，`cases/` 是 v1 真相目录

在 v1 中：
- `casebook` 表示逻辑层概念
- `cases/` 表示磁盘上的结构化真相目录

## D18. 实现阶段不再发明与 `cases/` 并列的持久化名词

实现中不允许再引入与 `cases/` 并列的持久化命名，例如：
- `casebook_store`
- `corpus_store`
- `incident_archive`

## D19. 上游评测系统只作为 artifact source / adapter target

One-Eval、lm-eval-harness、OpenCompass 或内部 harness 等上游系统，只能通过 adapter 进入 EvalShield canonical contracts。

它们的 report、score 或 workflow state 不能直接成为 EvalShield truth source。

## D20. One-Eval 是重要参照，不是 v1 依赖

One-Eval 证明 agentic eval workflow 会成为重要上游形态。

v1 预留 One-Eval-style provenance 字段和 reason codes，但不把完整 One-Eval adapter 作为 v1 阻塞项。

## D21. LLM 可以辅助解释，不能决定 TrustVerdict

对于 One-Eval 这类上游系统，LLM 可能参与 query understanding、benchmark selection、metric recommendation 或 report generation。

EvalShield 可以使用 LLM 生成 human report projection，但 `TrustVerdict` 必须来自 structured findings 与 rule-based verdict policy。

## D22. 四层信任链作为长期演进方向

EvalShield 的长期目标是建立四层信任链：
- Raw Scores（原始分数）
- Output Calibration（输出校准）— Phase 2
- Run Integrity（运行完整性）— v1 已覆盖，Phase 1
- Benchmark Validity（评测有效性）— Phase 3

演进采用双轨版本线：执行层（v1/v1.1/v2）和信任层正交，不互相绑定。
信任层用描述性名称，实施顺序用 Phase 1/2/3 表示。
详见 `EvalShield-架构演进路线图-v0.md`。

## D23. Benchmark Validity 消费 MIRAGE 论文的方法论

信任层 Benchmark Validity（Phase 3）采用 MIRAGE 论文（斯坦福李飞飞团队，2026）的方法论：
- 模态消融测试（Modality Ablation）
- B-Clean 基准清洗框架
- Visual Dependency Score（VDS）

EvalShield Benchmark Validity 超越 MIRAGE 的地方：推广到任意模态、持续运行的自动化 pipeline、machine-readable validity report。

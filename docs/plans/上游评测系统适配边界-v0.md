# 上游评测系统适配边界 v0

生成时间：2026-04-25。
适用范围：EvalShield v1。
文档类型：Reference。

## 目的

这份文档定义 EvalShield 如何面对 One-Eval、lm-eval-harness、OpenCompass、内部 PR-review harness 等上游评测系统。

它的目标是防止 adapter 需求把 EvalShield 推成通用 eval 平台。

## 核心立场

EvalShield 是 benchmark trust layer，不是 benchmark runner。

上游评测系统负责：

- 选择或构造 benchmark
- 执行模型 / agent
- 计算 raw score
- 生成原始报告

EvalShield 负责：

- 接收 run artifacts
- 归一化 canonical truth objects
- 检测 leakage / exploit / replay mismatch，以及 system family 下的 upstream provenance risk
- 生成 `TrustVerdict`
- 输出 evidence pack / replay bundle / case record

## 适配链路

```text
upstream eval system artifacts
        -> adapter validation
        -> source artifact digest
        -> canonical RunArtifact
        -> detectors
        -> TrustVerdict
```

adapter 的唯一目标是把外部 artifacts 收口为 EvalShield canonical contracts。

adapter 不能把外部系统的报告或结论直接提升为 EvalShield truth。

## Adapter 最小职责

每个上游 adapter 至少负责：

1. 识别 artifact bundle 类型与版本
2. 校验必需 artifact 是否存在
3. 生成 `source_artifact_digest`
4. 映射到 `RunArtifact`
5. 保留原始 artifact references
6. 明确记录缺失字段与 ingest notes
7. fail loud，而不是静默补默认值

## Adapter 不负责

adapter 不负责：

- 执行 benchmark
- 重新计算模型能力分数
- 选择 benchmark
- 推荐 metric
- 修改上游 artifacts
- 决定最终 `TrustVerdict`
- 直接生成 casebook truth

## 上游 provenance 字段

当上游系统是 agentic workflow runner 时，adapter 应尽量保留这些引用：

```text
provenance:
  upstream_runner_name: str | null
  upstream_runner_version: str | null
  upstream_workflow_trace_ref: str | null
  upstream_workflow_trace_digest: str | null
  upstream_schema_mapping_ref: str | null
  upstream_metric_plan_ref: str | null
  upstream_human_overrides_ref: str | null
  upstream_report_ref: str | null
```

这些字段是 provenance evidence，不是 EvalShield verdict source。

## 缺失上游 provenance 的默认解释

如果上游系统无法提供 workflow trace 或 raw evidence，EvalShield 不应假设结果可信。

默认策略：

- raw evidence 缺失：至少 suspect
- workflow trace 缺失：视上游类型与 benchmark 风险决定 trusted 或 suspect
- 只有 human report、没有 raw artifacts：suspect
- adapter 无法确认 score 来源：invalid 或 ingest error

具体 verdict 由 `判定策略矩阵-v0.md` 决定。

## v1 Adapter 优先级

v1 第一优先级仍是 PR-review benchmark adapter。

建议顺序：

1. internal / exemplar PR-review adapter
2. one concrete PR-review benchmark adapter
3. optional One-Eval output adapter design spike

One-Eval adapter 不应阻塞 v1 最小闭环。

## EvidenceRef 要求

adapter 产生的 provenance 风险 finding 必须使用 `system` family，并指向可复核证据。

允许的 evidence kind 包括：

- `metadata`
- `trace`
- `output`
- `diff`
- `prompt`
- `replay`
- `provenance`
- `workflow`

如果上游缺失证据，EvidenceRef 应指向缺失声明或 ingest validation record，而不是伪造 excerpt。

`workflow` kind 默认使用 `trace://` 或 `jsonpath://` pointer scheme。
`provenance` kind 默认使用 `jsonpath://run.provenance...` 或 `file://...` pointer scheme。
不为 v1 新增 `workflow://` 或 `provenance://` scheme。

## 明确不做

- v1 不做插件化 adapter marketplace
- v1 不做通用 event bus envelope
- v1 不做跨 benchmark family 的统一 runner API
- v1 不要求所有上游系统都提供 workflow trace
- v1 不把缺失 trace 自动等同于 invalid

## 设计结论

EvalShield 可以适配多种上游评测系统，但适配边界必须始终服务 canonical truth chain。

只要 adapter 开始承担 runner、metric recommender、workflow generator 或 verdict 决策职责，就已经越界。

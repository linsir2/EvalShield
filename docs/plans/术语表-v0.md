# EvalShield 术语表 v0

生成时间：2026-04-21。
作用：统一核心术语写法，避免后续文档轻微漂移。

## 术语

### Benchmark run

固定写法：

- `benchmark run`

含义：

- 一次具体评测执行及其产物集合

不要替换成：

- eval session
- benchmark job
- review attempt

### PR review benchmark

固定写法：

- `PR review benchmark`

含义：

- 面向 PR review / code review agent 的 benchmark 类型

### PR-review-agent

固定写法：

- `PR-review-agent`

含义：

- 在 PR review benchmark 中被评测的 reviewer agent

### Run trust

固定写法：

- `run trust`

含义：

- 一次 benchmark run 的结果可信度

注意：

- 它不是模型整体能力
- 它也不是通用 agent 安全性

### Canonical bundle

固定写法：

- `canonical bundle`

含义：

- EvalShield 内部的标准化 truth-source artifact 表示

### Canonical contract

固定写法：

- `canonical contract`

含义：

- versioned、digest-addressed 的对象契约定义

### Detector finding

固定写法：

- `detector finding`

含义：

- detector family 输出的一条结构化发现

### Detector family

固定写法：

- `detector family`

含义：

- 同类 trust-failure 检测器集合

v1 核心 trust-failure family 只允许三类：

- leakage
- exploit
- replay mismatch

上游 provenance 风险属于 `system` family 下的完整性风险，不是第四类 trust-failure family。

### Trust verdict

固定写法：

- `trust verdict`

含义：

- 机器权威输出：`trusted | suspect | invalid`

### EvidenceRef

固定写法：

- `EvidenceRef`

含义：

- 指向具体 supporting evidence 的结构化引用

### Pointer

固定写法：

- `pointer`

含义：

- `EvidenceRef` 中的机器可解析定位字符串

### Replay bundle

固定写法：

- `replay bundle`

含义：

- replay 尝试的结构化元数据与引用集合

### Structural replay

固定写法：

- `structural replay`

含义：

- 验证 run 结构与证据链可重建

### Behavioral replay

固定写法：

- `behavioral replay`

含义：

- 尝试验证 findings / verdict / review behavior 的相似性

注意：

- v1 不把它当硬承诺

### Casebook

固定写法：

- `casebook`

含义：

- 围绕 suspect / invalid runs 组织的结构化案例集

### Case record

固定写法：

- `case record`

含义：

- casebook 的原子结构化单位

### Exemplar

固定写法：

- `exemplar`

含义：

- v1 第一套固定 fixture 形态，用于收敛 adapter 设计


### Upstream eval system

固定写法：

- `upstream eval system`

含义：

- 产生 benchmark run artifacts 的外部评测系统，例如 One-Eval、lm-eval-harness、OpenCompass 或内部 PR-review harness

注意：

- 它不是 EvalShield truth source
- 它只能通过 adapter 进入 canonical bundle

### Agentic eval workflow

固定写法：

- `agentic eval workflow`

含义：

- 由 query understanding、benchmark selection、dataset mapping、metric recommendation、model inference、report generation 等节点组成的评测流程

### Workflow provenance

固定写法：

- `workflow provenance`

含义：

- 上游 eval workflow 产生 score 的路径证据，包括 node trace、schema mapping、metric plan、human override 和 rollback 记录

### Upstream provenance finding

固定写法：

- `upstream provenance finding`

含义：

- 由上游评测流程证据缺失、漂移或未审计人工介入产生的 system-family detector finding

注意：

- 它不表示模型能力失败
- 它表示 raw score 生成路径存在 trust 风险

### Artifact ingest

固定写法：

- `artifact ingest`

含义：

- 从外部 benchmark 产物进入系统、并进入 canonical normalization 的阶段

### Output Calibration（输出校准）

固定写法：

- `output calibration`

含义：

- 检测模型对自己答案的置信度是否准确的信任层
- EvalShield 信任层的 Phase 2

注意：

- 它不是 run integrity（Run Integrity 检测作弊，Output Calibration 检测校准）
- 它不依赖分布式执行（可以在 v1 上做）

### Benchmark Validity（评测有效性）

固定写法：

- `benchmark validity`

含义：

- 检测 benchmark 题目是否真的在测它声称要测的能力
- EvalShield 信任层的 Phase 3

### Modality Ablation（模态消融）

固定写法：

- `modality ablation`

含义：

- 通过移除特定模态输入（如图像），比较有/无该模态时模型准确率的差异
- 用于判断 benchmark 题目是否真正依赖该模态

### B-Clean

固定写法：

- `B-Clean`

含义：

- 基准清洗框架，剔除所有模型在无图条件下都能答对的题目
- 来源：MIRAGE 论文（斯坦福李飞飞团队，2026）

### Visual Dependency Score（视觉依赖度）

固定写法：

- `visual dependency score`
- 简写 `VDS`

含义：

- VDS = (有图准确率 - 无图准确率) / 有图准确率
- VDS ≈ 0 表示 benchmark 不依赖视觉，VDS ≈ 1 表示完全依赖

### Mirage Reasoning（海市蜃楼推理）

固定写法：

- `mirage reasoning`

含义：

- 模型在没有接收到某模态输入的情况下，仍然自信地描述该模态内容并进行推理
- 与 hallucination（幻觉）不同：幻觉是在正确框架内填充错误细节，海市蜃楼是构建完全虚假的框架

注意：

- 不要替换成 hallucination

### CalibrationReport

固定写法：

- `CalibrationReport`

含义：

- 单次 run 的输出校准报告对象
- 包含 ECE、overconfidence rate、逐题校准结果

### BenchmarkValidityReport

固定写法：

- `BenchmarkValidityReport`

含义：

- 单个 benchmark 的有效性报告对象
- 包含模态消融结果、B-Clean 结果、VDS

### 双轨版本线

固定写法：

- `双轨版本线`

含义：

- EvalShield 的演进沿两个正交维度：执行层（v1/v1.1/v2）和信任层（Run Integrity / Output Calibration / Benchmark Validity）
- 信任层用描述性名称，实施顺序用 Phase 1/2/3 表示
- 两个维度不互相绑定

## 术语使用规则

- 写设计文档时，优先使用本术语表中的固定写法
- 若需要中文解释，允许在首次出现时写：
  - `run trust（单次 run 的可信度）`
  - `canonical bundle（标准化真相包）`
- 不要在不同文档里为同一对象发明多个名字
